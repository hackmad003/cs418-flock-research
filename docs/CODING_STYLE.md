# Python Coding Style Guide

Follow these rules when writing or modifying Python code in this repo. Prioritize **readability, simplicity, and consistency** over clever solutions. Write code an undergraduate CS student can read and explain.

## 1. Most Important Rule

**Match the style of the existing codebase.**

When editing an existing file, keep its structure, naming, section banners, and commenting style. When creating a new file, follow this guide without adding extra documentation or complexity.

## 2. General Principles

- Prefer simple, readable code over advanced shortcuts (no clever one-liners).
- Do not add imports, functions, or abstractions the task does not need.
- Keep each function focused on one responsibility.
- Use type hints on function parameters and return values.

## 3. File Organization

Order every script like this:

1. Shebang (`#!/usr/bin/env python3`) when the script is run directly.
2. Module docstring: purpose, inputs, outputs, and how to run it.
3. Imports.
4. Constants and configuration (`UPPER_SNAKE_CASE`).
5. Functions, each in its own banner section.
6. `main()` function.
7. Entry point (`if __name__ == "__main__":`).
8. EOF banner.

Banner width is always the text length plus 4, so the `#` lines match the text line exactly:

```python
###########
# IMPORTS #
###########

#################
# GEOCODE PLACE #
#################
def geocode_place(place_name: str) -> tuple[float, float]:
    """Convert a place name into (latitude, longitude)."""
    pass

########
# MAIN #
########
def main() -> None:
    pass

###############
# ENTRY POINT #
###############
if __name__ == "__main__":
    main()

#######
# EOF #
#######
```

## 4. Imports

- One import per line, and remove unused imports.
- Add a one-line comment saying why the import is needed.
- Add the official documentation URL only the first time a library appears in the project or when it is likely unfamiliar. Do not repeat URLs for libraries already documented elsewhere in the repo.

```python
import csv  # https://docs.python.org/3/library/csv.html
# Used to read and write CSV files.

from pathlib import Path
# Used to build file paths that work on any operating system.
```

## 5. Comments and Documentation

Comment where it helps a reader understand, not on every line.

- Every function gets a short docstring stating its purpose.
- Add a comment before any block of non-obvious logic, and say **why** it is needed.
- Explain unfamiliar syntax, library calls, algorithms, and calculations. Add a small example when the logic is tricky.
- Do not comment code that is obvious from its name.

```python
# Keep only cameras made by Flock Safety. This creates a new DataFrame
# and leaves the original unchanged.
flock_cameras = cameras.filter(pl.col("manufacturer") == "Flock Safety")

# Sanity check: confirm the filter kept a reasonable number of rows.
print(f"Flock cameras found: {flock_cameras.height}")
```

## 6. Naming

- `snake_case` for variables and functions, `UPPER_SNAKE_CASE` for constants.
- Descriptive names over abbreviations (`camera_count`, not `cc`).

## 7. Files, Errors, and Data

- Use `pathlib.Path` for all file paths, anchored to the project root, not the terminal's current directory.
- Never overwrite an existing file unless explicitly asked.
- Validate important inputs before processing, and raise clear, specific error messages.
- In longer scripts, print progress messages and sanity checks (row counts, file written, etc.).
- Use **Polars** for tabular data and **GeoPandas** for geospatial data. Use pandas only when a library requires it, and say so in a comment.

## 8. Where Files Belong

Put new files in the directory that matches their purpose:

| Directory | What goes there |
|---|---|
| `src/cs418_flock_research/` | Reusable, importable code (functions used by more than one script or notebook). `loaders/` is for reading datasets, `processing/` is for cleaning and transforming them. |
| `scripts/` | One-time or run-from-the-command-line scripts, such as `fetch_*.py` downloaders and `create_dataset_samples.py`. Name them by action and source (`fetch_<source>.py`). Mark retired ones with a `_legacy` suffix. |
| `notebooks/` | Exploration and scratch work. Personal experiments go in `notebooks/personal_notebooks/`. |
| `checkpoints/<Stage>/` | Final, polished deliverables for each course checkpoint (for example `Exploratory_Analysis/`). Not a place for scratch work. |
| `data/raw/` | Downloaded datasets exactly as received. Gitignored, and never edited by hand. |
| `data/external/` | Small third-party reference files (Census boundaries, Chicago GeoJSON). |
| `data/processed/samples/` | Small `_sample` files generated by `create_dataset_samples.py`. Never edit by hand. |
| `docs/` | Written analysis and documentation (markdown). Assignment instructions live in Google Drive, not here. |
| `figures/` | Saved plots, with descriptive filenames. |
| `reports/` | Generated report outputs. |

Rules of thumb:

- If a notebook cell or script function gets reused, move it into `src/` and import it.
- Scripts import from `src/`. `src/` never imports from `scripts/`.
- Date-stamp downloaded raw files (`name_YYYY-MM-DD.csv`) so a refresh never overwrites older data.
- Do not put data files, generated outputs, or large files in `src/` or `scripts/`.
